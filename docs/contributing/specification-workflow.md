# 仕様駆動開発

Status: Active

目的は、期待する操作と結果を先に明確にし、それを実装・テスト・実画面の確認につなぐこと。
AGENTS.mdへ手順を増やすことや、文書の数を増やすこと自体を目的にしない。

## 基本の流れ

```text
依頼と対象範囲
  → 関係する仕様・知見を確認
  → 変更が必要なら提案を具体化
  → 書き終えてから別の観点でレビュー
  → 採用した仕様へ適用
  → 実装中の部分確認
  → テスト・実操作・AI画像レビュー
  → 結果を記録して完了
```

仕様作成、レビュー、実装は同じエージェント・同じ作業内で進めてよい。
別エージェントの起動や各段階でのユーザー承認は必須にしない。
外部リポジトリの個別の製品前提、公開・push等の権限、実行中の指示は継承しない。

## 仕様を作る範囲

- 新しい振る舞い、既存の期待結果を変える作業: [仕様ひな形](../specs/_template.md)で具体化する。
- Approved / Implemented仕様の意味を変える作業: [変更ひな形](../spec-changes/_template.md)に差分と理由を置き、採用後に正本を更新する。小さな変更は短い提案でよい。
- 既存仕様と異なる実装の修正: 受け入れ条件と回帰ケースを確認して実装へ進む。仕様変更提案は不要。
- 内部整理、誤字・リンク修正: 観察できる振る舞いを変えなければ新しい製品仕様は不要。
- 期待結果を既存仕様から決められない: 仕様の不足として整理し、テストに通る結果を後付けで仕様にしない。

## 最小の仕様

対象作業・対象外、操作前の状態、操作、観察できる結果、失敗/取消/回復、互換性への影響、
受け入れ条件と検証方法を書く。内部クラス・ピクセル値・回避策を必要なく要件へ固定しない。
ユーザーが明示した要求、希望、未確定の案、エージェントが選んだ判断を区別する。
判断には依頼との関係と理由を残し、ユーザーの発言として扱わない。

要件には `DBG-LIFE-001` のような安定IDを付ける。新規IDの前に [仕様一覧](../specs/README.md)を検索する。
UIシナリオの `UI-01`、テスト名、エラーコードとは区別する。
原則は一つの要件を一つの仕様が所有し、他の資料はリンクで参照する。

## 状態と採用

| 対象 | 状態 |
| --- | --- |
| 仕様の正本 | Draft → Proposed → Approved → Implemented |
| 既存仕様への変更提案 | Draft → Proposed → Approved → Applied、またはRejected |

Approvedは実装の判断基準として採用済み、Implementedは対象変更の実装と必要な証跡が揃ったことを示す。
過去の実装・テスト・発表資料が存在するだけでImplementedにしない。
採用済みの意味を変えた仕様は、今回の検証が揃うまでApprovedへ戻す。
Draft / Proposedを採用済みの仕様として実装しない。

提案を書き終えた後、[仕様レビュー](../../.agents/skills/review-spec/SKILL.md)を別passで行う。
作成者の頭の中の意図ではなく、依頼・文面・受け入れ条件を根拠に確認する。
レビューはBlocking、軽微な指摘、未決事項、採用可否を返す。

今回の依頼の範囲内で、重大な未解決事項がなく、互換性への影響と観察可能な受け入れ条件が明確なら、
エージェントが採用して実装へ進める。記録には `Approval mode: Agent-autonomous`、依頼の根拠、判断理由、レビュー結果を書く。
ユーザーの決定を根拠にする場合は `Approval mode: Human` と、実際に決定された内容を書く。

依頼範囲の重要な拡張、既存の許可で安全に判断できない互換性破壊、データ喪失、公開・権限等の境界、
製品の方向を大きく分ける未決事項だけは具体的な選択肢と影響を示して判断を求める。
「仕様レビューが終わったから」だけの確認待ちは作らない。公開やGit操作の許可を仕様の採用から推定しない。

## 実装・知見・検証への接続

受け入れ条件の表から、既存テスト・追加する回帰テスト・UIシナリオ・実装を追えるようにする。
すべてをテスト名へ埋め込んだり、単純な変更にも大きなfixtureを追加したりする必要はない。
実装中の確認と最後の合否は [UI検証ワークフロー](ui-validation-workflow.md) が所有する。
レポートには今回確認した要件IDと対象のソース状態を記録し、仕様の採用とテスト成功を区別する。

古い知見は [文書方針](documentation-policy.md) に従って利用する。
調査で得た再利用可能な発見は`knowledge`、採用した期待結果は仕様、設計理由はADR、重要な実行結果は`evidence`へ整理する。
Editor側の実装では、利用できる `build-unity-editor-extensions` の関連する部分を読む。
標準コントロールや実際のパネルで確認する手順を利用し、既存workaroundを無条件で増やさない。

長いタスクの再開地点は、変更提案または作業レポートへ対象仕様・未解決事項・残作業を短く残す。
すべてのタスクに専用のObjective / State文書を作る必要はない。再開時はGitの実態と現在の依頼を確認する。
