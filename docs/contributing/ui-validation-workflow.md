# UI検証ワークフロー

Status: Active

実装中の短い確認で問題を早く見つけ、完了直前に全体の整合性を確認する。
定型の操作・期待結果・画像レビュー基準を再利用し、毎回の探索や全コードの読み直しを減らす。
この手順はリポジトリの [AGENTS.md](../../AGENTS.md) の完了条件を具体化する。

## 1. 開始時に対象を決める

作業ツリー、Editorバージョン、既存Editorとそのproject / PIDを確認する。
変更対象に対応する下表のケースと、今回変える期待結果をレポートへ記載する。

振る舞いの期待結果は[採用済みの製品仕様](../specs/README.md)から選び、要件IDと今回のUIケースを対応付ける。
期待結果が決まらない変更は[仕様ワークフロー](specification-workflow.md)で具体化してから実装する。
要件の採用と今回のテスト成功は別の記録として扱う。

| 変更対象 | 実装中にまず確認するもの | 最終検証で追加するもの |
| --- | --- | --- |
| 文書・コメントのみ | 内容・リンク・該当する静的検査 | UIゲート対象外。表示や動作へ影響する設定変更はこの扱いにしない |
| 個別コントロール | 値・通知・通常/フォーカス/無効状態、狭い幅、両テーマ | 基本シナリオと影響ページの境界状態 |
| 共通USS/UXML・PanelSettings・テーマ | 代表ページ、狭い/広い幅、両テーマ、hover/focus | 全ページの両テーマ・狭い/標準幅、サイズ変更、Editorへの影響 |
| ナビゲーション・所有権・ライフサイクル | 遷移・戻る・同一ページ・終了/再初期化 | 深い/空/一時ページ、Editorとの切り替え、再生再開 |
| パッケージ設定・asmdef・リソース・サンプル | メタデータ・参照・コンパイル | 独立したGit導入先でサンプルのコンパイルと回帰テスト |
| CI・検証ツールのみ | 変更したコマンド・設定・結果判定経路 | 実行可能な範囲で実行確認。未変更のUIの再撮影は不要 |

局所変更でも、最終確認では以下の基本シナリオを確認する。共通部分に波及する修正へ広がったら、検証対象も更新する。
未検証のOS・Unity版・実機まで成功したと推定しない。

## 2. 実装中は影響箇所を短く確認する

1. コンパイルと関連テストを実行する。
2. 実際のUnityで対象の画面を開き、変更に対応する入力・状態遷移を試す。
3. 画像を見て、値・UI階層・resolved bounds・Consoleと照合する。
4. 問題があれば修正し、該当ケースを再実行する。操作結果を検査できる不具合は回帰テストへ残す。

例えば幅の修正なら320×568、色ならDefault/Darkのhover/focus、遷移なら子ページ→戻るを確認する。
毎回全ページの撮影や独立したAIレビュー工程を実行する必要はない。
通常の確認は作業中のエージェントが画像を直接見てよい。

## 3. 操作と撮影の条件を揃える

- 検証シーンは `Assets/Development/Scenes/DebugUIValidation.unity`。起動後、メニュー位置・ページ・値を既知の初期状態にする。
- Unity版、OS、描画API、入力方式、フォント、テーマ、描画解像度を記録する。Game Viewのズーム表示と実際の描画解像度を区別する。
- 時刻・乱数・動的な値は固定するか比較範囲から除外し、除外理由を記録する。
- 画像はレイアウトと遷移アニメーションの完了後に撮影する。状態をポーリングする場合もタイムアウトを設け、待機超過を失敗として残す。
- 要素は `qa-nav-inputs` 等の安定した名前で識別する。座標入力が必要なら、現在の要素の表示範囲から座標を求める。
- 入力テストは実際のポインター/キーボード経路を通し、実行後の値・通知回数・画面状態を確認する。`value` の代入やコールバックの直接呼び出しだけで「クリック確認済み」としない。
- Game ViewとEditorウィンドウは別の描画対象として扱う。カメラだけの画像でオーバーレイUIの確認を済ませない。
- 設定やEditorPrefs等の初期値を控え、終了時に戻す。ユーザーの未保存シーンで検証しない。

## 4. 完了直前の確認範囲

UI・コード・アセットの変更では、まずパッケージ検査と `Lilja.DebugUI.Tests` 全体を実行する。
テスト件数・失敗・スキップ数を実行結果から記録する。失敗や意図しないスキップを隠さない。
配布に影響する場合は独立したGit導入先の検証も行う。

### 画面の組み合わせ

| 対象 | 最終確認の基本範囲 |
| --- | --- |
| ランタイムの各ページ | 1280×720、Default/Dark。Home、Text and selections、Numbers and sliders、Vectors and bounds、Groups and dynamic UI、Long content、Empty、Deep navigationを撮影 |
| 狭い画面 | 320×568、Default/DarkのHomeと影響ページ。共通レイアウト・テーマ変更なら全ページ |
| その他の画面 | 390×844、768×1024、1920×1080でHomeを確認。リサイズ前後と影響ページも必要に応じて追加 |
| Editorウィンドウ | Lightで幅480px、Darkで幅800px。Homeと影響ページを操作・撮影。Editorだけの変更はこの画面群を中心に検証 |

ランタイムのみ/Editorのみの局所変更は、変更のない側をHomeで切り替えるスモーク確認までに絞れる。
対象外の組み合わせには理由を記録する。全解像度×全状態を毎回総当たりする必要はない。
画像内に収まらない項目はスクロールして追加撮影し、上端の画像だけで下部まで確認済みとしない。

### 基本シナリオ

| ID | 操作 | 期待結果・撮影状態 |
| --- | --- | --- |
| UI-01 | 起動→Primary/Secondary/Danger→Disabled | 初期表示が読める。各有効ボタンでActionCountが1回増加し、無効ボタンで増加しない |
| UI-02 | Text and selectionsで日本語入力、Enum/Radio/Toggle、Tab/Submit | 入力値と選択状態が一致し、通知が重複しない。通常/フォーカス/hoverの文字が読める |
| UI-03 | NumbersとVectorsで値・成分・スライダー端点を編集 | 編集結果が保持され、ラベルと成分が対応する。進捗0/50/100%の文字と領域が見える |
| UI-04 | Groupsで入れ子を開閉→Addを複数回→Remove | 開閉が一致する。動的行が追加・解放され、空のVirtualFoldoutに余白が残らない。並び順は10/20/30 |
| UI-05 | Long contentを最後までスクロール→Last row action | 最終行に到達してボタンが反応する。スクロールバーが操作できる |
| UI-06 | 子→深い階層→戻る→Home、空/一時ページ、同一ページへ再遷移 | タイトル・履歴・表示が一致し、空ページでも戻れる。一時ページが蓄積しない |
| UI-07 | ヘッダードラッグ→解像度縮小→位置復元→ResetPosition | メニューとヘッダーへアクセスでき、既定位置へ戻せる |
| UI-08 | 外側クリック→既定の複数回クリックで再表示、timeScale=0で遷移 | 表示/非表示と入力受付が一致する。時間停止中も操作・遷移が完了する |
| UI-09 | Editorを開く→操作→ランタイムへ戻す→停止/再生、Shutdown/再初期化 | ページの所有権が切り替わり、古い表示・重複・例外が残らない。停止時に案内が出る |

自動テストで同じ内部状態を確認済みなら、その結果を証跡として参照できる。
実際の入力経路や描画の確認を省いた場合は、その範囲を区別して記録する。

## 5. 最後にAIが画像をレビューする

AIへの入力は、今回の目的・意図した表示変更、ケースごとの期待結果、最終状態の実画像、テスト/Console結果とする。
比較可能な基準画像があれば基準・現在・差分を併せて渡す。ソース全体の再読解を毎回求めない。
複数画像をまとまった単位でレビューし、実装中に全件レビューを繰り返さない。
差分画像だけでなく画面全体も見る。基準画像に既にある問題も検出対象とする。

以下の固定項目で確認する。

1. **可読性**: 文字の欠け・化け、読めないコントラスト、必要情報の見切れがない。
2. **配置**: 意図しない重なり・画面外配置・過大な空白・折り返し不良がない。
3. **対応関係**: ラベルと値・成分・選択肢の対応が分かる。
4. **操作状態**: 有効/無効、選択、開閉、フォーカスが見分けられる。操作後の画像が期待結果と一致する。
5. **一貫性**: テーマ、サイズ、ランタイム/Editor切り替えで意図しない崩れがない。EditorはUnityの標準操作・表示と整合する。

### レビュー指示の定型文

```text
添付したケース別の実画像を、可読性・配置・対応関係・操作状態・一貫性で検証する。
今回の意図した変更と各ケースの期待結果を判断基準にする。
機能や必要情報へのアクセスを妨げる問題はFAIL、軽微な改善提案はNOTEとする。
画像から判断できない項目はUNVERIFIEDとし、実操作済みとは推測しない。
各指摘にはケースID、画像名、要素または領域、観察した問題、期待結果を記載する。
問題がなければ確認したケースとPASSを記録する。新しいデザイン要求は作らない。
```

作業エージェント自身に画像認識能力があれば、このレビューを行ってよい。別モデルや外部サービスの呼び出しは必須ではない。
画像を見られない実行環境ではAIレビューは `UNVERIFIED`。テキストログだけで代用しない。

## 6. 合否と修正後の扱い

| 判定 | 条件 |
| --- | --- |
| PASS | 必須ケース、テスト、画像レビュー、終了確認が成功 |
| PASS_WITH_NOTES | 必須項目は成功。機能・可読性・必要情報へのアクセスを妨げない軽微な指摘のみ残る |
| FAIL | テスト失敗、操作不能、値/通知/履歴の誤り、必要な文字の欠け・読めない配色、重なりや見切れで必要操作ができない等が残る |
| UNVERIFIED | 必須項目の未実行、画像不足、判定不能、実行環境不足、終了未確認等が残る |

AIの疑わしい指摘は、要素の境界・実操作・追加画像で確かめる。自動的な基準画像更新や無限の再レビューで処理しない。
見た目の好みだけの提案でタスクを際限なく広げない。未解決の必須項目をNOTEへ格下げしない。
意図した表示変更に合わせた基準画像更新は、その変更が要件と一致し正常に操作できることを確認して記録する。失敗を消すための更新は禁止。

修正後は該当ケースと関連テストを再実行する。共通USS/制御コードの修正は影響する画面群と回帰テスト全体を再確認する。
実行後に動作・描画へ影響する変更を加えたら、古い結果はその部分の最終証跡として使わない。
文書だけの変更ではUI画像の再撮影は不要。

## 7. 証跡と終了処理

証跡は `artifacts/validation/<run-id>/` に分け、過去の実行結果を上書きしない。
[レポートのひな形](ui-validation-report-template.md) をコピーし、次を保存する。

- HEADのコミットIDとdirty状態。未コミットの検証なら差分・未追跡の対象ファイルも保存し、検証した内容を特定できるようにする。
- 実行環境、ケース一覧と合否、入力/設定、テスト結果とConsoleログ、ケース名で識別できる画像、AIの指摘。
- 比較時は基準画像の版、許容差、除外範囲と理由。初回で基準がない場合はその旨を記載し、画像比較済みとは報告しない。
- 未検証項目と理由、終了確認。PRには要点と再現手順を記載する。必要な証跡をPRに添付する場合は機密情報を含めない。

将来の調査に残す価値がある結果の要約は`docs/evidence/`、再利用する技術的な発見は`docs/knowledge/`へ整理する。
保存する基準と確認状態は[文書方針](documentation-policy.md)を参照し、生ログや通常のタスク報告を毎回恒久文書へ複製しない。

Play Modeと今回開始した継続処理を停止し、今回の成果を保存する。
変更した検証用のテーマ・位置・解像度等を復元し、今回起動した不要なEditorを通常終了する。
PID/projectを照合してEditor・専用ワーカーの終了を確認する。既存Editorは閉じず、残る理由を報告する。
失敗・タイムアウト・中断・回答待ちでもこの片付けを行う。

## 現在の実装範囲

自動化済みなのは、パッケージ検査、Test Runnerの回帰テスト、独立導入先の生成とCI設定。
CIのUnityジョブにはREADMEに記載したライセンス設定が必要。
検証シーンは操作・撮影対象を提供するが、全シナリオの自動入力・一括撮影・画像比較・AI判定を一括実行するランナーはまだない。
当面は利用可能なUnity CLI/Editor操作とComputer Use、画像の直接レビューで本手順を実行する。
CI成功、画像保存、過去の[検証記録](../evidence/2026-10-21-debug-ui-validation.md)のいずれかだけで、今回の完了ゲート通過とはしない。

### 既存の検証コマンド

リポジトリ直下で実行する。以下のUnityコマンドは、対象プロジェクトのEditorとPipeline接続が利用できる場合に使う。
接続がなければTest Runnerを使うか、起動・終了ルールに従って対象Editorを起動する。

```sh
python3 .github/scripts/validate_package.py
unity status --format json
unity command run_tests --mode editor --filter Lilja.DebugUI.Tests --async_tests true --timeout 300 --caller plugin --skill unity-cli --project-path "$PWD" --format json
```

非同期実行の開始成功は、テスト成功ではない。次で完了を確認し、結果を保存する。

```sh
unity command test_status --caller plugin --skill unity-cli --project-path "$PWD" --format json
unity command console_status --caller plugin --skill unity-cli --project-path "$PWD" --format json
```

繰り返し確認する際は適切な間隔と実行上限を設ける。
画像撮影・AIレビュー・独立Git導入先の検証はこれらのコマンドに含まれない。
独立導入先の生成はREADMEの `prepare_consumer.py` の手順を使用し、生成後にそのプロジェクトでテストを実行する。
