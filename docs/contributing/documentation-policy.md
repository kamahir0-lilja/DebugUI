# 文書の配置・保持・更新

Status: Active

文書の入口は [docs/README.md](../README.md)。資料は古さだけで判断せず、役割と確認範囲で扱う。
内容を追加する前に、同じ情報を既存の置き場所へ追記できるか確認する。

| 内容 | 置き場所・状態 | 維持するもの |
| --- | --- | --- |
| 製品の振る舞い・受け入れ条件 | `docs/specs/`。状態は[仕様ワークフロー](specification-workflow.md)を参照 | 現在採用している期待結果 |
| 採用済み仕様の変更案と採用理由 | `docs/spec-changes/` | 正本への適用先と採用の根拠。適用後の詳細はGitで追える |
| 開発・検証の手順とひな形 | `docs/contributing/`。手順はStatus: Active、ひな形は編集用 | 現在実行する手順。運用が変わったら更新する |
| 横断的な設計選択の理由 | `docs/adr/`、Status: Accepted / Superseded | 選択肢、理由、帰結。置換時は新しいADRへつなぐ |
| 再利用する技術調査・ハマりどころ | `docs/knowledge/`、Status: Reference | 現象、適用条件、観察と仮説、対処、確認範囲 |
| 特定の実行で確認した結果 | `docs/evidence/YYYY-MM-DD-topic.md`、Status: Historical | 対象状態、日時、環境、結果、根拠、未確認範囲 |
| 発表・説明用の過去資料、退役した調査 | `docs/archive/<種類>/`、Status: Archived | 出典と当時の内容。現行の設計・手順を追従させない |
| 局所的な回避策・処理順序の理由 | 実装付近のコメント | 将来の変更で壊しやすいWHY。必要な資料だけリンクする |
| 回帰の再現 / 生の実行結果 | テスト / `artifacts/validation/<run-id>/` | テストは更新し、ログ・画像は実行単位で保存する |

同じ要件や完了基準をAGENTS.md、スキル、仕様、レポートへ複写しない。
日常の作業報告をすべて恒久文書へ複製しない。`evidence`へ残すのは、重要な基準確認、
設計判断を支える実測、再発調査に役立つ結果など、将来参照する理由がある要約に絞る。
`archive`を未分類資料の置き場にせず、再利用する調査は`knowledge`、現行ルールは本来の正本へ整理する。

## 開発フローにおける残し方

1. **調査中**: 生ログ・画像・試行は実行単位のartifactsへ。非自明で他の修正でも役立つ発見だけ、[技術メモひな形](../knowledge/_template.md)を使って既存メモへ追記するか、新しいメモにする。
2. **採用時**: 守るべき操作結果は仕様、複数箇所に影響する設計理由はADR、局所のWHYは近接コメント、再発条件はテストへつなぐ。技術メモはその根拠へのリンクを持ち、仕様本文を複写しない。
3. **完了時**: 検証結果を[レポート](ui-validation-report-template.md)へまとめる。恒久保存する価値がある場合だけ、対象状態を固定した短い要約を`evidence`へ残す。
4. **関連実装を変更するとき**: 今回触る箇所のメモ・コメントの前提を確認する。条件が変われば確認範囲を更新し、方式を退役させたらその旨と置換先を示す。毎回すべての過去資料を読み直す必要はない。

## 技術メモの確認状態

`Status: Reference`は調査用の参考資料であり、採用済み仕様という意味ではない。
別に`Verification`と、その対象となる環境・ソース状態・確認日を示す。

- `Current`: 記載した対象状態・条件で確認済み。その状態以外まで保証しない。
- `Historical`: 過去の観察として記録され、現行状態での再確認はしていない。
- `Unknown`: 対象状態や確認結果を十分に復元できない。分からない項目は「未記録」とする。

複数の条件を含むメモは節ごとに確認範囲を示せる。一部の再検証で文書全体をCurrentへ変えない。
今回移した古い技術メモはHistoricalとし、Git保存日を実測日や最終検証日に読み替えない。

再利用時は関係する節の前提と現行コードを照合する。同じ条件で有効な証跡があるなら参照できる。
条件が異なる場合は実パネル・入力・resolved style等で再確認する。
「USSでは制御できない」「focusableをfalseにする」等の対処は、全Unity版・全コントロールの規則ではない。
食い違いがあれば適用範囲や訂正を明記し、過去の観察を現在も検証済みとしない。

## 検証記録・アーカイブの保持

検証記録には、日時、対象SHA（dirtyなら差分等）、環境、確認結果、証跡の所在、未検証範囲を残す。
後日得た新しい結果は別の日付・runとして記録し、古い成功/失敗を新しい結果へ上書きしない。
記録漏れを後から補う場合も、当時未記録だったことと補足の根拠を区別する。
ローカルのGit管理外ログしかない場合は、その制約も示す。参照先の画像が誰でも取得できると推定しない。

アーカイブは出典、元の用途、元のパス、既知なら作成時点を冒頭に示し、現行の参照先へ案内する。
本文の過去の断言・失敗した案を今の事実へ書き換えない。現行向けの説明が必要なら仕様・メモ等へ書く。
旧`src/`の記述を当時の説明として残す場合も、現行パスが分かる入口を付ける。
移動後はリポジトリ内のリンク・URLを更新し、旧位置に本文の重複コピーを残さない。履歴はGitで追う。

## 実装付近に残す理由

通常の代入や分岐の説明は不要。将来の単純化で不具合が戻る処理だけ、
必要な順序・壊れる挙動・テストや仕様への参照・回避策を外せる条件を簡潔に書く。
根拠が変わったら説明も確認し、不要になった回避策と古い説明を一緒に整理する。
実装ファイルを変更した理由を長い恒久レポートへ毎回書き写す必要はない。

## 継続的な確認

`python3 .github/scripts/check_docs.py` は文書リンク、要件IDの重複・参照、仕様の状態と、
knowledge / evidence / archiveの分類・確認状態の記載を検査する。
この構造検査は、仕様の内容・採用判断・Unity上の表示や挙動を検証するものではない。
Unityの起動・検証の要否は変更内容に合わせて判断し、文書のためだけに起動しない。
